# レンタルスペースALBE 予約システム ― 構築概要（Webサイト連携 議論用）

> **目的**：Webサイトのリニューアル／このシステムとの融合を別スレッドで議論するための「引き継ぎ資料」。
> このシステムが**何を持っていて**、**Webサイトとどう繋げられるか**、**シームレスな予約導線**をどう作るかを検討するための材料です。
> 最終ゴールは「お客様ができるだけ迷わず・スムーズに予約を完了できること」。

作成日：2026-08-15 ／ 対象：レンタルスペースALBE（9スペース・株式会社ファーストクリエイト）

---

## 0. これは何か（30秒サマリー）

- WordPress + Bookly を置き換える**自社開発の予約システム**。
- **Cloudflare Workers 上で動く1つのアプリ**が、予約API・会員機能・決済・管理画面・お客様向け画面まで一体で提供。
- 予約台帳の「正」は**Googleカレンダー**（スペースごとに1カレンダー）。ダブルブッキングを多層で防止。
- 決済は **Stripe（カード／銀行振込／コンビニ）＋ PayPal**。決済先行フロー（払った瞬間に予約確定）。
- 現状ほぼ全機能が実装済み・テスト済み。**残るは主にWebサイト連携（＝今回の議論）**。

## 1. 技術構成

| レイヤー | 技術 | 補足 |
|---|---|---|
| 実行基盤 | **Cloudflare Workers**（`albe-booking-api`） | エッジで動くサーバーレス。常時起動・自動スケール |
| APIフレームワーク | TypeScript + **Hono** | 1 Worker に API と静的HTML配信を同居 |
| DB | **Cloudflare D1**（SQLite互換） | 会員・予約・決済・ポイント等 |
| お客様/管理 画面 | 素の **HTML + JavaScript**（`public/*.html`） | ビルド不要・軽量・高速。Workerが直接配信 |
| カレンダー | **Google Calendar API**（サービスアカウント） | 予約台帳の唯一の正。5分ごとに双方向同期 |
| メール | **Resend** | 予約確認・変更・リマインド・お礼 等の自動送信 |
| 決済 | **Stripe** ＋ **PayPal** | カード即時／銀行振込／コンビニ（本番設定待ち） |
| 定期実行 | Cron（`*/5`＝カレンダー補正、`0 0`＝日次メール/保持ポリシー） | |

> **連携上の重要ポイント**：フロントは「重いフレームワーク（React等）」ではなく**軽い静的HTML**。
> そのため、Webサイト側の技術（WordPress後継 / 静的サイト / ヘッドレスCMS など）を**選ばずに繋ぎやすい**。

## 2. このシステムが「持っている」お客様向け画面

現状、Workerが配信している公開ページ（＝Webサイトと役割分担を考える対象）：

| 画面 | パス | 役割 |
|---|---|---|

| **サイネージAPI** | （API） | 店頭ディスプレイ向けの空き状況表示 |

## 3. お客様の予約フロー（＝“シームレス”の核心）

```
[入口] Webサイト or 予約トップ or スペース別リンク
   │
   ▼
① スペースを選ぶ（9スペース）      ← Webの各スペース紹介から直リンク可（?space=）
   ▼
② カレンダーで日時を選ぶ（30分単位・営業時間内・空き枠のみ）
   ▼
③ オプション/人数/利用目的 などを入力
   ▼
④ 会員 or ゲストの分岐
     ├─ 「会員登録して予約」（クーポン/ポイント/チケット/振込が使える）
     └─ 「登録せず予約（ゲスト）」（カード即時決済のみ）
   ▼
⑤ 決済（Stripeカード / PayPal / ＜会員＞銀行振込・コンビニ）
   ▼
⑥ 決済先行で確定 …「支払った瞬間に予約成立」
     └─ 決済直前に他のお客様に枠を取られていたら→自動で不成立＆返金
   ▼
⑦ 完了画面＋確認メール（Googleカレンダーにも自動反映）
```

**シームレス化に効く既存の仕組み**
- **スペース別ディープリンク**（`?space=`）：Webの紹介ページ→そのスペースの予約に1クリックで飛べる。
- **ゲスト予約**：会員登録なしでもカード決済で即予約完了（離脱を減らす）。
- **決済先行＋自動返金**：「予約したのに未払い」「払えなかったのに枠が埋まる」を解消。
- **モバイル対応**の軽量ページ：スマホからの予約が主流でも軽快。
- **会員は次回から入力短縮**（登録情報・履歴・クーポン/ポイント）。

## 4. Webサイトとの「融合」オプション（議論のたたき台）

このシステムは Worker 上にあり、**同じWorkerで通常のWebページも配信できる**ため、融合の自由度が高いです。代表的な4案：

| 案 | 概要 | 長所 | 短所/論点 |
|---|---|---|---|
| **A. 別サブドメイン誘導** | Webは `space-albe.com`、予約は `yoyaku.space-albe.com` に分離しリンクで送客 | 実装が最速・責務が明確 | ドメインを跨ぐ＝会員ログイン（Cookie）の共有に工夫が要る／“サイト内で完結”感は弱い |
| **B. スペース別ディープリンク送客**（Aの発展） | Webの各スペース紹介ページ →「このスペースを予約」で `?space=` に直リンク | 既存機能でそのまま実現・導線が短い | 予約自体は予約側ドメインで行う |
| **C. 埋め込み（iframe/ウィジェット）** | Webページ内に予約UIを埋め込み、ページ遷移せず予約 | “サイト内で完結”＝一番シームレス | 実装・保守コスト、SEO/計測、モバイル高さ調整などの検討が必要（現状**未実装**＝要開発） |
| **D. 同一Workerで全ページ配信** | マーケ用ページも予約もこの Worker（同一ドメイン）で配信し統合 | Cookie/会員が完全に一体・完全シームレス・1ドメイン | Webの制作・更新フロー（CMS/デザイン運用）をどうするか要設計 |

> **観点**：シームレスさ（D>C>B>A）と、制作/運用のしやすさ・SEO・移行コストのトレードオフ。
> 「マーケ/ブランディングのページ運用を誰がどう更新するか」がD/C採用可否の分かれ目。

## 6. 連携で必ず論点になる技術ポイント

- **会員ログインのCookieスコープ**：
  会員セッションはこのシステム（D1）が管理。**同一ドメイン（案D）なら会員状態を完全共有**、別ドメイン（案A）だと共有に一工夫（サブドメイン間Cookie、またはSSO的な仕組み）が必要。
- **アカウントの一本化**：Web側に別ログイン（CMS会員等）を作らない方が、お客様の混乱と二重管理を避けられる。**会員の“正”はこのシステム**に寄せるのが素直。
- **デザインの統一**：予約画面のCSSはこのシステム内。Webの新デザインに合わせて**予約画面も同じ見た目に寄せる**と“サイト内で予約している”体験になる（案C/Dで特に重要）。
- **Googleカレンダーが台帳の正**：Web側が独自に空き状況を持つのは非推奨。空きは常に予約システム（→カレンダー）に問い合わせる。
- **スマホ実機での導線**：入口（Web）から決済完了までの**モバイル1本道**を最優先に設計。
- **現状のBASIC認証ゲート**：ステージング保護のため一時的にかけている（本番公開時に外す/調整）。

## 8. 別スレッドで詰めたい問い（議論のスターター）

1. **統合の型**は A/B/C/D のどれを軸にする？（シームレスさ vs 制作/運用コスト）
2. Webサイトは**別ホスト（CMS等）**にする？ それとも**この Worker で一体配信**（案D）にする？
3. **ドメイン設計**：`space-albe.com` 直下で予約まで完結？ サブドメイン分離？
4. **会員アカウントは一本化**（このシステムを正）でよい？ Web側ログインは作らない方針でよい？
5. 現行サイトの**どのページを残し／どれを予約システムに寄せて削除**する？
6. 予約画面の**デザインを新サイトに合わせて作り直す**範囲は？（ロゴ/配色/フォント/写真）
7. **入口の置き方**：トップの「予約する」CTA、各スペースページの「このスペースを予約」ボタンの配置。
8. **計測/SEO**：予約完了のコンバージョン計測、スペースページのSEOをどう担保する？
