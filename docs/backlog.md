## 口コミ投稿で100ポイント付与（要相談・未着手）

**概要**：会員が口コミを投稿したら、お礼として **100ポイント** を付与する仕組み。

**着手前に決めること（次回相談）**：
- **対象の口コミはどれか**（作りが大きく変わる最重要ポイント）
  - (A) **Google口コミ** … 会員が Google に口コミ投稿 → 「投稿しました」と申請 → 管理者が確認 → 付与
  - (B) **サイト内の独自口コミ** … システム内に口コミ投稿フォームを設け、投稿を保存・表示
- **承認制にするか**（推奨：承認制。空投稿・不正・重複防止のため）
- **付与回数の上限**（推奨：会員1人につき1回まで）
- **付与ポイント数**（想定：100pt）
- （サイト内口コミの場合）口コミの**公開・非公開**、表示場所、星評価の有無

**技術メモ（着手時の想定）**：
- ポイント残高・履歴の既存テーブル／仕組みを流用できるか確認する。
- 承認制なら管理画面に「口コミ承認 → ポイント付与」導線が必要。
- スキーマ変更を伴う場合は `migrations/` に新ファイル → 「DB migrate」ワークフローを staging → production の順で実行（CLAUDE.md のルール）。

## 新規会員登録特典クーポン（実装済み・既定OFF／開始時期は保留）

**概要**：新規会員登録で対象スペース限定の割引クーポンを自動発行。悪用は「対象スペース限定＋1人1枚＋期限」で抑止。

**v1仕様（実装済み・ステージング反映済み）**：
- 特典：新規会員登録で **¥500クーポン** を自動発行（`discount_coupons`／`source='signup'`）。
- 対象：**名駅防音室A・B／東別院24h**（`signup_bonus_rules.space_ids` のJSONで指定。**データ駆動＝将来 名駅フリー¥1,000 等を行の追加/編集で拡張可**）。
- 割引：fixed / ¥500 / `total_hours=1`（1予約で使い切り＝1回のみ）。防音室・東別院は1時間3,000円超なので¥500は必ず満額。
- 期限：登録日〜**1ヶ月以内に「予約」**すれば利用可（`valid_until=登録日+validity_days`。クーポン期限は"予約作成日"で判定＝利用日は先でもOK）。
- 使い方：予約画面で**自動候補表示**（`GET /api/mypage/usable-coupons?spaceId=`／押すとコード欄へ自動入力）。マイページ・管理画面の顧客詳細にも表示。
- 悪用対策：1顧客1枚＋**電話番号/メール重複で二重発行ブロック**＋対象スペース限定＋期限。
- 対象：新規会員のみ（既存99名は対象外）。

**開始方法（"すぐ実行"の手順）**：
- `signup_bonus_rules.enabled` を **0→1** に切り替えるだけで発動（コード改修不要）。
- 本番未反映の場合は「本番デプロイ＋DB migrate(production)」後に enabled=1。

**Phase 2（運用を見て必要なら）**：
- メール確認の必須化／登録Turnstile／使い捨てメール拒否。
- 管理画面から特典ルール（対象スペース・金額・期限）を編集するUI。
- ウェルカムメールに特典クーポンを明記。
- 名駅フリー ¥1,000 OFF の展開（同じ仕組み。ルール行を追加）。

## 30分刻み予約への対応（要検討・保留）

**背景（なぜやりたいか）**：
- 競合が予約を **30分刻み**にしてきた。
- **スペースマーケット／インスタベース**が30分刻みで予約できる。→ 合わせた方が運用（オペレーション）しやすい。
- 対象想定：名駅防音室A・B／東別院。

**検証結果（2026-09-06時点・重要）**：
- **「1時間料金÷2」だけの設定変更では不可**。現在の課金は `ceil(実利用時間)`＝**1時間単位に切り上げ**のため、単価を半分にすると **60分が半額**になってしまう等で破綻する。
- 正しくやるには「**課金単位を1時間→30分（0.5時間）に変える**」料金エンジンの改修が必要（単価は現状維持）。
- 時間選択UIは**既に30分刻み**なので変更不要。変えるのは課金ロジック。
- **チケット・クーポンに影響あり**：どちらも時間（整数）ベース。充当ロジック `coveredAmountForHours` が `Math.floor` で端数切り捨て／`remaining_hours` が整数カラム／チケット商品は「◯時間券」販売。→ **0.5時間対応の改修＋テスト**が必要。新規登録¥500クーポン（1回使い切り）も残0.5で使い切り判定が崩れる。
- **1日料金**（=day_rate_hours×単価）は、単価÷2にすると半額化する副作用。課金単位30分案（単価維持）なら影響なし。
- 最低利用時間（整数運用）も0.5対応が必要になる場合あり。

**推奨アプローチ（実行時）**：
- 内部を **「分」または「30分コマ」単位に統一**するのが本来きれい（料金・チケット・クーポンを一貫して扱える）。
- 手順：課金単位30分化 → チケット/クーポンの端数対応（or 分管理へ移行）→ チケット消費ルール明文化（◯時間券＝30分×N）→ 最低利用0.5対応 → マイグレーション（残時間の単位変更）→ テスト → ステージング先行検証。
- 規模感：**中〜大**（料金エンジン中核＋チケット/クーポンへ波及）。
