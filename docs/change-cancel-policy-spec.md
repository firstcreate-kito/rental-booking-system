## 0. このメモの目的

改定した「予約変更ポリシー／キャンセルポリシー」を、システムのどこに・何を追加し、どう判定し、どんな文言を出すかを1枚にまとめる。
着工前の認識合わせが目的で、**このメモに合意が取れてから実装に入る。**

---

## 1. 基本方針（大原則）

- システムは **「セルフ操作を受け付けてよいか」の可否判定** と **画面表示・案内** のみを担う。
- **金額の計算・徴収・返金には一切踏み込まない。** 振込手数料・カード手数料3.6%・料金区分UP差額は、すべて最終的に**人が精算**する。
- 判定はすべて **「当初予約金額」と「当初利用日」** を基準にする（変更後の値ではない）。
- セルフ操作の入口（ゲスト用ページ・会員マイページ）で判定NGなら**ブロックしてメールフォームへ誘導**する。
- **管理画面（スタッフ操作）はこの制限を免除**（当日でも減額・キャンセル・日程変更を実行可能）。

---

## 2. データモデルの追加（実装の土台・最重要）

判定を「当初予約」に固定するため、`booking_groups` に2カラムを追加する。既存の `total_amount`（現在の合計）と `reschedule_count`（実装済み）はそのまま使う。

### 追加カラム（新規マイグレーション: `0023_booking_original_snapshot.sql` 想定）

| カラム | 型 | 意味 | 書き換え |
|---|---|---|---|
| `original_total_amount` | INTEGER | **当初予約金額**（作成時の合計・税込） | **不変**（作成時のみ） |
| `original_date` | TEXT (`YYYY-MM-DD`) | **当初利用日**（複数日予約は最初の利用日） | **不変**（作成時のみ） |

### バックフィル（既存データ）

- `original_total_amount` ← 既存 `total_amount` の現在値
- `original_date` ← その予約グループの `bookings` 内、最も早い `date`
- ※既存予約は「当初＝現在」とみなして初期化する。過去の変更履歴は遡及しない。

### 書き込みタイミング

- 予約グループ作成時（Web予約・管理者作成の両経路）に確定値をセットする。
- **以後、変更・日程変更・オプション追加のいずれでもこの2カラムは更新しない。**
- シード（`seed.sql` / seeds）にも同じ2カラムを追加して整合させる。

## 3. 判定ロジック（システムが実際に判定する4つ）

判定に使う共通値:
- `daysBefore` = 当初利用日 `original_date` − 本日（**暦日**で数え、**前日を1日前**とする。既存 `todayJST()` 等を使用）
- `remainRatio` = 変更後合計 ÷ `original_total_amount`（当初金額に対する**累計**の残存割合）

### 3.1 増やす（時間追加・日数追加）

- **常に受付可**（空き枠がある限り）。空き判定は既存の空き枠ロジックを流用。
- 当日の時間追加も可（現地精算のため、システムは受付のみ）。

### 3.2 減らす（時間短縮・日数削減）

当初金額に対する**累計**の残存割合で無償セルフ可否を判定する。

| 当初利用日までの残日数 | 無償セルフ操作の範囲 |
|---|---|
| 31日以前（`daysBefore >= 31`） | 制限なし（いくら減らしてもセルフOK） |
| 30〜15日前（`15 <= daysBefore <= 30`） | 変更後が当初の **50%以上残る** 範囲でセルフOK |
| 14日前〜前日（`1 <= daysBefore <= 14`） | 変更後が当初の **80%以上残る** 範囲でセルフOK |
| 当日（`daysBefore <= 0`） | **減らす操作は不可**（一律ブロック） |

- 判定は「1回ごと」ではなく **累計**。常に `remainRatio`（変更後合計 ÷ 当初金額）を閾値と比較するので、複数回に分けて減らしても当初基準で正しく効く。
- 範囲を超える減額は**セルフ不可 → メールフォーム誘導**（減少分にキャンセル料が発生する旨を案内。金額はシステムでは出さず「担当者よりご案内」）。
- 一度減らした分を元に戻す（増やす）のは 3.1 に従い**空き次第で可**。

### 3.3 日程変更

| 当初利用日までの残日数 | 挙動 |
|---|---|
| 31日以前（`daysBefore >= 31`） | **当初予定日 `original_date` の前後1ヶ月以内**への振替をセルフ受付 |
| 30日前以降（`daysBefore <= 30`） | セルフ不可 → キャンセル＋新規扱いの案内（メールフォーム誘導） |

- 振替可能な範囲は `original_date − 1ヶ月 〜 original_date + 1ヶ月`。範囲外はブロック。
- 当日は日程変更不可（キャンセル扱いの案内）。
- ※「1回まで無償」は `reschedule_count`（実装済み）で回数を把握できるが、**回数によるブロックはしない**（後述 4. の通り「2回まで」は表示のみ・機械的には不問）。

### 3.4 キャンセル（全体）

- キャンセル料テーブルは **`src/lib/cancellation.ts` に実装済みで改定ポリシーと数値が完全一致**（`[{30,50},{14,80},{0,100}]` = 31日前0%／30-15日50%／14-前日80%／当日100%）。**作り直し不要。**
- **セルフキャンセルの受付停止ライン（決定済み）: 利用日の「3日前以降」はセルフキャンセル不可 → フォーム誘導。**
  - 具体的には `daysBefore <= 3`（3日前・2日前・前日・当日）はブロックしフォームへ誘導。`daysBefore >= 4`（4日以上前）はセルフキャンセル可。
  - 直前キャンセルはネット受付を避け、キャンセルチャージを口頭で案内できるようにするための措置。
- キャンセル料の**実額計算・返金は人が処理**。システムは「キャンセル料が発生する場合は手続き前に金額をご案内します」の**案内表示まで**。
- **申し込み画面での事前表示（決定済み）:** 変更・キャンセルの**申し込みを始めた時点**で、キャンセルポリシー／3日前ラインの案内を**先に表示**する（NG後の事後表示だけにしない）。「利用日の3日前以降はオンラインでのキャンセルを受け付けておりません。メールフォームよりご連絡ください」等。

## 4. あえて機械化しないもの（人の運用に残す）

| 項目 | 対応 |
|---|---|
| 振込手数料の額 | 計算・表示しない（人が精算） |
| カード手数料 3.6% | 計算しない（人が返金時に処理） |
| 料金区分UP差額（平日→土日祝） | 自動徴収しない（現地/個別精算） |
| 返金の実処理・口座聞き取り | すべて手動 |
| 繰り返し利用者のお断り | 自動判定しない。悪質は**ブラックリスト手動移行**（既存機能を使用） |
| 無償変更「2回まで」 | 画面には **「2回まで」と明記するが、回数によるブロックはしない**（機械的には不問） |
| 災害等の特例 / 連日・複数日・定期利用の個別調整（見積） | 人が個別対応 |

## 5. 判定を差し込む場所（エンフォースメント・ポイント）

セルフ操作の入口は現状2つ。両方に**同一の判定ロジック**を噛ませる（共通関数化して重複を避ける）。

1. **ゲスト用 `/booking-change/` ページ**
   - 3点照合（メール・電話・予約番号）で予約を呼び出す既存フロー（`src/routes/guest-change.ts` / `src/lib/booking-change-page.ts`）。
   - 現状は「変更リクエストを送るだけ」なので、**減らす／日程変更のセルフ確定を入れるかどうか**は要判断（下記「残・要決定」）。少なくとも「範囲内か超過か」を判定し、超過ならフォーム誘導文言に切り替える。
2. **会員マイページ** のセルフ変更・キャンセル
   - `src/routes/bookings.ts` の `POST /:number/cancel`・`POST /:number/reschedule`・`POST /:number/options` の手前で判定。

- **管理画面（Bearer認証・スタッフ）経由は判定を免除**（`c.get('admin')` があるルートはスキップ）。

### 判定NG時の統一メッセージ（案）

> この内容はオンラインでのお手続き範囲を超えています。
> キャンセル料が発生する場合がございますので、お手続き前に担当者より金額をご案内します。
> お手数ですが、メールフォームよりご連絡ください。

## 6. 実装ステップ（着工後の順序・目安）

1. マイグレーション `0023`（`original_total_amount` / `original_date` 追加＋バックフィル）、シード整合。
2. 予約作成経路で2カラムをセット（Web・管理者）。
3. 判定ロジックを純粋関数として新規追加（`src/lib/change-policy.ts` 想定）＋ユニットテスト。
   - 入力: `daysBefore`, `originalTotal`, `newTotal`, 操作種別（増/減/日程変更/キャンセル）
   - 出力: `allowed` / `reason` / `mode`（'self' | 'form'）
4. マイページ（`bookings.ts`）のセルフ操作前に判定を差し込み。
5. ゲスト `/booking-change/` に判定を反映（範囲内/超過で文言分岐）。
6. 画面文言（「2回まで」明記・統一NGメッセージ）反映。
7. wrangler dev + Playwright/curl でシナリオ検証 → コミット/プッシュ。

## 7. 決定事項（確定・この内容で着工）

以下すべて確定済み。**Phase 1 は「セルフ確定を新設せず、リクエスト＋範囲判定の文言表示」を基本とする段階導入。**

1. **ゲスト `/booking-change/`（決定）:** 当面「**リクエスト送信＋範囲判定の文言表示**」に留める。範囲内でもセルフ確定は新設しない（従来どおり変更リクエストを送る）。範囲超過なら文言をフォーム誘導に切り替える。
2. **セルフキャンセルの受付停止ライン（決定）:** 利用日の**3日前以降（`daysBefore <= 3` ＝ 3日前・2日前・前日・当日）はセルフキャンセル不可 → フォーム誘導**。`daysBefore >= 4`（4日以上前）はセルフキャンセル可。当日は明確に不可。
3. **日程変更・減額のセルフ確定（決定）:** Phase 1 では**セルフ確定を自動化しない**。マイページ・ゲストとも「範囲内/超過の判定＋文言表示」に留め、確定処理はスタッフ運用に回す（段階導入。将来 Phase 2 でセルフ確定を検討）。

### Phase 1 の実装レンジ（この範囲で着工）

- `original_total_amount` / `original_date` の追加・不変保存・バックフィル（§2）。
- 判定純粋関数（§3の4ルール）＋ユニットテスト。
- **申し込み画面の入口で**ポリシー／3日前ラインを事前表示（§3.4）。
- ゲスト `/booking-change/`・会員マイページの変更/減額/日程変更フローに**範囲判定＋文言分岐**を差し込み（セルフ確定は新設しない）。
- 会員マイページの**セルフキャンセルのみ** 3日前ラインでゲート（`daysBefore <= 3` はブロック＋フォーム誘導、`>= 4` は従来どおりセルフ実行）。
- 管理画面（スタッフ）は全判定を免除。
- 「無償変更2回まで」は文言のみ明記（回数ブロックなし）。

### Phase 2 以降（将来・今回は対象外）

- 範囲内なら**セルフ確定**まで自動化（減額・日程変更）。
- 必要に応じてゲスト画面でのセルフ確定。
